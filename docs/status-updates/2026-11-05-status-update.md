# Status Update — BabyBlue — 2026-11-05

## Summary
BabyBlue is a South African healthcare booking platform (patient booking + practice management) built as three layers: a Next.js 16 frontend, a thin .NET 9 API, and a Postgres/Supabase schema that holds all real business logic as 106 stored procedures. No production database is provisioned yet — everything today runs against an in-browser PGlite demo database, with the .NET API layer built and tested but not yet deployed in front of real traffic. Overall health is strong: 185/185 frontend tests, 90/90 API unit tests and 56/56 API integration tests all pass; the database has real defense-in-depth (RLS + composite-FK isolation, an EXCLUDE constraint preventing double-booking at the data layer, append-only consent records for POPIA compliance); and the project's own documentation (`DECISIONS.md`, `PROGRESS.md`) is unusually rigorous. The single biggest gap is that **frontend auth was never migrated to the dual-mode (API vs. demo-DB) pattern the rest of the app follows** — if a real API is ever pointed to, login will still silently succeed against the local demo database and then fail every subsequent real API call. The second-biggest gap, already flagged in the project's own `IMPROVEMENT_PLAN.md`, is that **no concurrency test exists for double-booking or double-holding a slot** — the two most safety-critical properties in the whole system are unverified under real concurrent load.

## Architecture
**What's there, and working well:**
- Clean three-layer split: Next.js UI → thin .NET controllers → Postgres stored procedures. The .NET layer enforces this boundary *mechanically*, not just by convention: `api/tests/BabyBlue.Api.Tests/ArchitectureBoundaryTests.cs` uses reflection to fail the build if `BabyBlue.Api` ever references Npgsql/Dapper types directly, or if `BabyBlue.Contracts` references the data layer.
- Tenant/session context flows correctly through the API: JWT → `CallerContextMiddleware` → `SessionContext.ApplyAsync`, which sets `search_path`, role, and timeouts via `set local` inside the open transaction (`api/src/BabyBlue.Data/Npgsql/SessionContext.cs:44-53`) — so nothing leaks onto a pooled connection for the next request. This is the correct pattern for RLS session variables under connection pooling.
- Frontend's dual-mode data layer (`src/lib/api/{practice,growth,platform,patient,public}.ts`) consistently branches `hasRemoteApi() ? call API : import("@/local/db")`, with the demo-DB import kept dynamic so PGlite/Worker code never ships in a server bundle.
- Output caching (`api/src/BabyBlue.Api/Caching/PublicReadCache.cs`) is scoped correctly — only anonymous GET/HEAD with no Authorization header, varied by host+brand, refused if the response sets a cookie. No cross-tenant cache-leak vector found.
- Database defense-in-depth is real, not just documented: composite-FK tenant isolation *and* RLS (D-04), a BEFORE INSERT/UPDATE trigger *and* a function-level gate on the verified badge (D-06), and a Postgres `EXCLUDE USING gist` constraint preventing double-booking at the data layer rather than in application code (D-05, confirmed at `supabase/migrations/0001_core_schema.sql:180,199`).

**Where it's leaky:**
- `src/local/auth.ts` (`signIn`, `signUp`, `useSession`) has no `hasRemoteApi()` branching at all — it unconditionally runs against the local PGlite `auth.*` tables. Every other module assumes `uid` becomes a real bearer token once an API is configured; nothing produces one. This is the one place the "19 files migrated to procedure calls" story has no real-mode implementation.
- The demo chrome — `DbGate` (boots a full browser Postgres), the "demo environment" banners, and three "reset demo data" buttons (`src/components/patient/PatientRoot.tsx:25,41-48,45`, `src/components/os/OsRoot.tsx:30,190-199,165`, `src/app/patient/account/page.tsx:101`) — mount unconditionally, with no `hasRemoteApi()` check. Only the practice-activation shortcut and the asset-download fallback are actually guarded, contrary to the docs' implication that all demo-only code paths are gated.
- `IMPROVEMENT_PLAN.md`'s own "Tier 0 — blocking" checklist (§17) is stale against the code: items like `revoke execute from public`, `force row level security`, the 4NF rewrite, the 106 procedures, price snapshot on appointments, and the slot-hold quota trigger are **already implemented** in `supabase/migrations/0007_4nf_and_106_procedures.sql` — the plan document just wasn't updated after that migration landed. The plan even contradicts itself: §16 cites `appointments.price_cents` as done while the Tier-0 table still lists it as outstanding.

## Where things stand
- **API layer**: all 106 of 106 planned endpoints are routed and tested (90 unit + 56 integration tests, confirmed by actually running `dotnet build`/`dotnet test`, not just reading docs). No TODOs, no `NotImplementedException`, no stubs found anywhere in `api/src` or `api/tools`.
- **Database**: all 106 procedures exist and are grant-mapped correctly (10 public_* + 13 patient_* + 62 practice_* + 16 growth_* + 6 platform_* = 106, verified by counting grant statements). RLS, FORCE RLS on personal-data tables, search_path pinning on every `security definer` function (169 functions checked, zero gaps), and grant hygiene (no function executable by `PUBLIC`) are all in place.
- **Frontend**: the product UI (patient booking, practice OS) has been migrated off raw SQL — verified independently by grepping `src/app`/`src/components` for raw table access: zero matches outside two documented, guarded exceptions. 185/185 Vitest tests pass; `npm run typecheck` passes clean.
- **Not yet started / explicitly deferred** (per `ROADMAP.md`, consistent with what the agents found): no Supabase project is provisioned, so there is no live database behind any of this; Supabase Auth is not wired to the frontend's real session flow (see auth gap above); slot alerts, "claim a listing," payments, reviews, and native mobile are all explicitly future-later items, not partially-built ones.
- **Demo-only, by design and correctly isolated**: the legacy "Flow" queue demo (`src/app/c`, `/q`, `/staff`) imports neither the real API client nor the local demo-DB module used by the real product — it's a separate fictional-data sandbox, not a half-migrated feature.

## Risks: things that could fail unexpectedly
Ranked most-severe first.

1. **Auth will silently misbehave the moment a real API is configured.** `src/local/auth.ts` has no remote-mode branch (file above). Trigger: set `NEXT_PUBLIC_API_BASE_URL` to point at the real .NET API. Consequence: login succeeds against the browser's local demo database, producing a local demo UUID; every subsequent `src/lib/api/*` call then sends that UUID as a bearer token to the real API, which will reject it (401s across the board) — this will look like the entire backend is broken when it's actually just auth.
2. **No concurrency test exists for the system's two most safety-critical guarantees.** `IMPROVEMENT_PLAN.md §18` already names this: all 82+ database tests run on a single PGlite connection, so `no_double_booking` and `no_double_hold` — both enforced by Postgres `EXCLUDE` constraints — have never been exercised under real concurrent load. Trigger: two patients racing to book or hold the same slot in production. The constraint itself should hold (it's database-enforced, not app-logic), but the *surrounding* retry/error-handling path (slot_unavailable messaging, hold-quota behavior under contention) is completely unverified.
3. **Error paths on read queries are invisible to users.** `src/local/hooks.ts`'s `useQuery` correctly captures `{ data, error, loading }`, but every one of ~29 page/component call sites across both patient and practice OS screens never reads `.error`. Trigger: an RLS denial, dropped connection, or 500 on any data-fetching call. Consequence: the screen just quietly keeps showing stale or empty data with no error banner or retry — a user or staff member has no way to know the data they're looking at is wrong or missing. Only mutation paths (button clicks) surface errors via `friendlyError()`/toast; reads do not.
4. **Demo chrome will ship to real users if the API-mode gate is incomplete elsewhere.** `DbGate`, the demo banners, and the three "reset demo data" buttons have no `hasRemoteApi()` guard. If any real deployment relies on the assumption that "demo-only code is gated," this specific set of UI is the exception — a real patient could see "every practitioner, patient and figure is fictional" and a button that wipes local state.
5. **No Content-Security-Policy header.** `next.config.mjs` sets `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`, and HSTS, but no CSP. Lower severity than the above (no XSS vector was found), but worth closing given this handles health-adjacent PII.
6. **Minor: a hardcoded fallback log-hashing salt.** `api/src/BabyBlue.Api/Middleware/RequestLoggingMiddleware.cs:14-15` falls back to a literal default salt if `Observability:UserHashSalt` is unset, with no startup failure. Only weakens the one-way user hash in logs (not a real secret, not PII exposure on its own) — but a misconfigured production deploy would silently use it.
7. **Stale `.next/` type cache after the recent front-door route split** can produce spurious `Cannot find module` typecheck errors for anyone who doesn't clear it after pulling `jam/front-door-split`. Not a repo bug (both paths are gitignored), but worth a one-line note in CONTRIBUTING.md since it will confuse the next person who typechecks without a clean build.

## Security notes
This was a lightweight pass (full audit available via the `007`/`security-review` skill if wanted), but it was thorough across all three layers:
- **No committed secrets anywhere in the repo** — grepped for AWS/GitHub/Google token patterns, PEM keys, and real Postgres connection strings; `.env.example` has only placeholders; `.gitignore` correctly excludes `.env*.local` and `.data/`.
- **JWT validation is solid**: issuer/audience/lifetime/signing-key all validated, and the algorithm is explicitly pinned per configured secret type, blocking `alg: none` and HMAC/RSA-confusion attacks (`api/src/BabyBlue.Api/Auth/SupabaseJwtSetup.cs:45-76`).
- **CORS has no wildcard-plus-credentials exposure**: brand-scoped exact-match origin allow-list, and `AllowCredentials()` is never called anywhere in the API.
- **SQL injection surface is essentially nil**: only one `EXECUTE format(...)` block in the entire schema (`0007_4nf_and_106_procedures.sql:2774-2789`), used for re-granting extension-function privileges from catalogue queries — not attacker-influenced. Every one of the ~169 `SECURITY DEFINER` functions pins `search_path = public`, closing the classic Postgres privilege-escalation hole with zero gaps.
- **A caller-supplied brand-selection header exists** (`BrandResolutionMiddleware.ResolveEffectiveHost`) that lets a request pick its tenant via `X-Tenant-Host`/`Origin` on shared platform hosts. The code's own comment argues this is safe because RLS still scopes rows by `auth.uid()` regardless of which brand is selected — consistent with what was independently found on the database side (RLS + FORCE RLS on all personal-data tables), so the claim checks out, but it's the one place where the API-layer and database-layer trust boundaries meet and is worth a second look together rather than in isolation.
